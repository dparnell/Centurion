# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Verilog re-implementation of the Centurion minicomputer's CPU6 board — a microcoded, Am2900 bit-slice CPU from the late 1970s. The design is a *gate-level-faithful* model: modules and signals are named after the physical chips on the original board (`// Microcode pipeline F5/H5/J5/K5/L5/M5 74LS377`, `// J10 Link/carry mux 74LS151`). The real microcode ROM image (`Verilog/roms/CodeROM.txt`, 2048 × 56-bit) and opcode map ROM (`Verilog/roms/CPU-6309.txt`) are dumps from the original hardware and drive everything — the CPU's instruction set lives in those files, not in the Verilog.

The RTL and the `make` targets live in [Verilog/](Verilog/); run all `make`
commands from that directory. Two other directories hold everything that is not
RTL: [Verilog/asm/](Verilog/asm/) is the *source* to the programs that run on
the machine (`forth.s`, the `probe*.s` instruction-set experiments, and the
FORTH test scripts), and [tools/](tools/) is the Python — the assembler and
disassembler, the microcode and VCD tools, and the scripts that drive the real
board. `Verilog/programs/*.txt` is build output from `asm/`, plus the handful of
hand-written hex programs that predate the assembler. Every tool in `tools/`
resolves repository paths from its own location, so it can be run from anywhere.

## Commands

```
make test                       # build + run the Icarus Verilog simulation testbench
make                            # synthesize for Tang Nano 9K (yosys -> nextpnr-himbaechel -> gowin_pack)
make load                       # build and program the board: diag, on the auxiliary test menu
make load-tos                   # the same ROM with the switches set for the TOS monitor
make load-forth                 # assemble asm/forth.s and build and program that instead
make programs                   # assemble every asm/*.s into programs/*.txt
make clean
python ../tools/Microcode.py    # disassemble roms/CodeROM.txt to stdout
python ../tools/parse_vcd.py    # microcode-level trace from vcd/CPUTestBench.vcd -> vcd/CPUTestBench.txt
python ../tools/ControlPanel.py # Tk GUI that steps through vcd/CPUTestBench.vcd cycle by cycle
make psramtest                  # just the PSRAM PHY, against a behavioural HyperRAM die
```

The toolchain (`iverilog`, `vvp`, `yosys`, `nextpnr-himbaechel`, `gowin_pack`, `openFPGALoader`) comes from [oss-cad-suite](https://github.com/YosysHQ/oss-cad-suite-build), installed at `~/.local/oss-cad-suite/bin`.

`make test` runs the whole suite (`hellorld`, `bnz_test`, `alu_test`) in one `vvp` invocation. To run a *single* program, edit the `initial` block in [CPU6TestBench.v](Verilog/CPU6TestBench.v) — each test is a `$readmemh("programs/X.txt", ram.rom_cells)` followed by a reset pulse; several (`diag`, `inst_test`, `cylon`, `blink`) are commented out and use a fixed `#delay` instead of the `sim_end` handshake.

The `Not enough words in the file for the requested range` warnings from `$readmemh` are expected — the programs are much smaller than the 8K ROM array.

The `$dumpfile` writes `CPUTestBench.vcd` into the Verilog directory, but both Python VCD tools look for `vcd/CPUTestBench.vcd` — move it there first.

### Simulation tracing

Tracing is off by default. Uncomment the `` `define `` lines at the top of [CPU6TestBench.v](Verilog/CPU6TestBench.v) and rebuild:

- `TRACE_I` — one line per instruction with all registers (also pulls in `Instructions.v` for mnemonics)
- `TRACE_UC` — microcode sequencer jumps/ORs
- `TRACE_WR` / `TRACE_RD` — bus writes/reads

## Architecture

### Module wiring

There is no filelist; modules are pulled in with `` `include `` from whichever top level you build. Two top levels share the same `CPU6` core:

- [CPU6TestBench.v](Verilog/CPU6TestBench.v) — simulation. Its `Memory` module provides ROM at `0x08000`, RAM at `0x0b000`, low RAM at `0x00000`, plus hardcoded reset vector and Diag-board responses. A write to `0x3f201` prints a character (fake UART); a write of `0x01` to `0x3f900` ends the test.
- [tangnano9k.v](Verilog/tangnano9k.v) — synthesis. A power-on reset holds `reset` for 1024 board clocks after configuration, then it follows the (pulled-up, active-low) reset button. Everything is clocked from the 27 MHz `in_clk` pin — a single clock domain on a real pin-driven global. `ClockEnable` then gates the core to the original CPU6's 5 MHz by accumulation (5 enables every 27 clocks, exact with no drift) rather than by division, since 27 is not a multiple of 5. `Divide4` is left in the file but unused: driving a fabric-generated clock onto a global through a `BUFG` did not work on hardware, so slow the core with an enable, never a second clock domain. There is no PLL: `PsramSdr` builds its own 6.75 MHz bus clock out of four phases of the 27 MHz clock, so the whole design is one clock domain. `AddressDecode` picks the peripheral and a single `assign data_r2c = mux_select ? mux_data : ram_data` feeds the CPU's read bus — every readable peripheral drives its own `data_out` and **nothing else may drive `data_r2c`**. `BoardMemory` answers everything the `MUX` UART board at `0x3f200` does not claim: 8K of ROM at `0x08000` preloaded from `programs/diag.txt` (change that `$readmemh` to run something else), 4K of RAM at `0x0b000`, and 4K of low RAM at `0x00000` — the last of which sits under the CPU's own register file and mapping RAM, so writes there land in both. `LEDPanel` at `0x5c00` is write only and has no read port. Holding `btn2` only triggers the status dump; it no longer changes the core's speed, so it does not perturb what it is measuring. Any such speed control has a hard floor of two board clocks between enabled cycles, because the microcode ROM reads every clock. `Watchdog` runs off the 27 MHz clock and takes over the LEDs if `CPU6` stops pulsing `instruction_start`; its stalled display is LED1 blinking at 1 Hz, LED2 = reset asserted now, LED3–LED6 = the highest microcode address reached since reset divided by 128. Every diagnostic input is an ordinary fabric signal on purpose — an earlier version sampled the CPU clock net itself and nextpnr could not route a global to a LUT data input, so that bit read as a false zero. `PsramSdr` drives the embedded HyperRAM and works on hardware, but is still exercised by `PsramTest`'s own self test rather than by the CPU — putting it on the bus is the next step.

`Clock.v` and `Instructions.v` are simulation-only.

### Inside CPU6.v

[CPU6.v](Verilog/CPU6.v) is the heart of the design and where nearly all work happens. The 56-bit microcode word from `CodeROM` lands in the `pipeline` register; every field of that word is decoded into the named 74-series decoders (`d2d3`, `e7`, `h11`, `k11`, `e6`) and drives the datapath enables shown in [images/Datapath.png](images/Datapath.png) (source: `datapath.excalidraw`).

- **Microsequencer**: three chained instances — two `Am2909` (address bits 3:0 and 7:4) and one `Am2911` (bits 10:8) — produce the 11-bit microcode ROM address. Conditional branching works by OR-ing bits into the low address nibble (the `J13`/`K13` muxes) rather than by computed jumps.
- **ALU**: two `Am2901` 4-bit slices (`alu0`, `alu1`) chained into an 8-bit ALU, with separate shift/carry muxes between them.
- **Instruction decode**: the opcode on `DPBus` indexes `MapROM` (the 6309 PROM), which yields the microcode entry point. Microcode address `0x101` is the start of each instruction — `instruction_start` and the tracing hooks key off it.
- **MMU**: the 8-bit page table maps `memory_address[15:11]` + `page_table_base` to a 19-bit physical address. On the original this is two 93L422 4-bit RAMs; here it is split into four 128-entry arrays (`page_table_{lo,hi}_{even,odd}`) specifically so it fits the Tang Nano 9K. This lookup is unpipelined and dominates LUT usage — most of the design's logic cells go here.
- **The bottom of physical memory is the CPU's own state, not the bus.** `0x000`-`0x0ff` is the register file, answered inside `CPU6` rather than from `dataInBus`. `0x100`-`0x1ff` is **not**: it is ordinary RAM, and there is no memory mapped window onto the mapping RAM anywhere. Software reaches the page file only through the `PAGE` instruction. The table's index order is still not free — `page_address` must be `{page_table_base, memory_address[15:11]}`, because that is how both directions of `PAGE` address an entry; the reverse order translates perfectly well and hides the problem until something walks the table.

Files follow the two Verilog coding guidelines quoted in the comments: blocking `=` in combinational `always @(*)`, nonblocking `<=` in sequential `always @(posedge clock)`.

### Programs

`programs/*.txt` are hex bytes, one per line, with `//` comments, loaded via `$readmemh` into the testbench ROM (linked at `0x8000`). The older ones are hand-assembled; anything substantial is now written in [asm/](Verilog/asm/) and assembled with [Assemble.py](tools/Assemble.py), which emits exactly that format so nothing downstream changed. `make run SRC=asm/forth.s IN=asm/tests_forth.f` assembles a source and runs it on the whole simulated board.

## Notes

- **What a bitstream was built with is not a file, so make cannot see it change.** `PROGRAM`, `DIP` and `PSRAM_SELFTEST` all change what synthesis produces while leaving every source file untouched, so `make load-forth` straight after `make load` used to find `tangnano9k.json` up to date and program the board with **diag** instead - the wrong build, silently, which is the worst kind of thing to be debugging. `build.stamp` records the three and forces a rebuild when they differ. Note that `make -n` cannot show this working: the stamp's recipe only rewrites the file when the configuration actually differs, and a dry run assumes every recipe ran, so it prints a full rebuild either way. Time a real run instead - an unchanged configuration takes 0.008s.
- **Serial settings are per program, and the data bits matter as much as the baud.** `programs/serial.txt` uses the MUX power-on default, 9600 7E1; `programs/diag.txt` reconfigures the channel on startup to **19200 7N1**, so `picocom -b 19200 -d 7 -p n /dev/ttyUSB1`. Leaving off `-d 7` gives 8N1, which reads a 7-bit character's stop bit as data bit 7 and delivers every byte as `data | 0x80` — high-bit garbage that looks like a baud problem but is not. diag prints its banner once and then waits, so open the terminal first and press reset.
- **The missing first character is the terminal, not the MUX.** diag prefixes each screen with `ESC FS FF` — in the ROM at `0x8dc2` the bytes are `9b 9c 8c` with the high bit set, which is `1b 1c 0c` on a seven bit channel — and `ESC` followed by `0x1c` is not a valid ANSI sequence. A terminal starts parsing at the `ESC`, never finds a legal final byte, and swallows the next printable character, which is why picocom shows `PU-6 MAPPING RAM TEST` and `UXILIARY TESTS`. The byte stream itself is complete: a `hexdump` of the same output shows `0c 1b 1c 41` with the `A` present, and reading the port over libusb shows the full text. Nothing in `mux.v` needs fixing, and the machine's own output can be trusted. To read it cleanly, strip the escapes: `tr -d '\033\034\014'`.
- The LEDs show the LED panel register, and all eight blink together at 1 Hz if `CPU6` stops executing. The bring-up diagnostics that once shared them — a 1 Hz clock reference, a readout of the MUX's selected line settings, and a standalone `0x55` generator on `btn2` that bypassed the CPU and MUX entirely — were removed once the board worked, but are in the history and are worth restoring if a board ever goes quiet again.
- **Debug logic is state too, and the same reset rule applies to it.** The status dump's pass counter and its first-failure latch were only initialised at configuration, and the latch is set-once, so after a button reset the dump still reported the first run's number and could never update. That made a single unrepeated measurement look like a result that reproduced across a reset, and across four different designs, which sent a whole day's debugging down the wrong path. Distrust any diagnostic that reports the same value after a change that should have moved it.
- **Everything with state must follow the core's reset, not just the core.** The MUX had no reset at all and the page table was only initialised at power-up, so diag's mapping RAM test passed once and then failed on every run after a reset: it came back to a serial channel still mid-character and a page table still holding the previous run's patterns. "Works once, then always fails after a reset" is the signature of state surviving a reset — look for registers and memories the reset does not reach.
- Holding `btn2` prints the CPU's position over the serial line at diag's 19200 7N1 (see [StatusDump.v](Verilog/StatusDump.v)): the last two instruction fetches, whether a byte is waiting and the last one received, a count of every byte the receiver has completed, and the page table base and mapping. It freezes that snapshot when the machine has printed nothing for two seconds while still fetching. This is what found the fault above — four hex addresses that decoded to diag's wait-for-a-character loop — after LED-based guessing had got nowhere.
- **Do not drive the board over libusb and through `/dev/ttyUSB1` at the same time.** The whole build, load, run, capture cycle can be scripted without any tty: `openFPGALoader` programs over libusb and pyftdi can open the UART channel of the same FT2232 with `serial_for_url('ftdi://ftdi:2232:/2', baudrate=19200, bytesize=7, parity='N', stopbits=1)`, which sidesteps the `uucp` group entirely. The cost is that pyftdi detaches `ftdi_sio` to claim the interface, and afterwards picocom on `/dev/ttyUSB1` reads garbage even though the board is transmitting perfectly: the chip is fine and the driver's view of it is not. A `USBDEVFS_RESET` ioctl on the device node under `/dev/bus/usb` can be issued without root and rebinds the driver, but it did not fix the tty path; a physical replug did. Agree who has the board before either side takes it.
- **When the console looks like garbage, check the raw bytes before blaming anything.** `stty -F /dev/ttyUSB1 19200 cs7 -parenb -cstopb -crtscts raw -echo` followed by `timeout 8 hexdump -C /dev/ttyUSB1`, with the reset button pressed a second later, reads the boot banner directly and takes the board, the driver and the terminal program apart in one step. On one occasion this showed a perfectly clean menu while picocom on the same port with the same nominal settings showed garbage, which put the fault in picocom's own configuration rather than anywhere in the machine. Worth knowing too that diag opens its banner with `0c 1b 1c`, a form feed then `ESC FS`, so a terminal that has already been fed binary can stay wedged and render good data as noise; `reset` clears that.
- **To tell a wrong line setting from a wrong baud, count the high bits.** Reading the same boot banner three ways gives 427 bytes at 7N1 with no high bits set and 99% printable, and 427 bytes at 8N1 with **every** byte high-bit set and nothing printable. A wrong baud garbles the byte count as well; a wrong data-bit count preserves it exactly and just sets bit 7 on everything.
- **If the serial port goes silent, unplug and replug the board before suspecting the design.** `openFPGALoader` detaches the FTDI kernel driver to program over channel A, and it can leave channel B — the UART on `/dev/ttyUSB1` — delivering nothing even though the FPGA is transmitting correctly. This cost a long debugging session in which the RTL, the netlist, the pin placement and the board's own LEDs all said the design was working. A USB re-enumeration clears it. Holding `btn2` drives the UART pin from a standalone `0x55` generator with no CPU or MUX involved, which separates this class of fault from a real design fault in one step.

- The README's synthesis section still describes the older iCE40 / Alchitry Cu target (and `LEDPanel.v`'s comment still mentions Alchitry). The Makefile and current work target the Gowin GW1NR-9C on the Tang Nano 9K; pin assignments are in [tangnano9k.cst](Verilog/tangnano9k.cst).
- README says `make all` for simulation, but `all` is the synthesis target — use `make test`.
- **Never let a block RAM's output be the thing a clock enable holds.** A BRAM output is not a register: with `CE` low it is not refreshed, and the value decays. This cost two rounds of hardware debugging. `CodeROM` had an async read, so yosys absorbed CPU6's `pipeline` register into the BRAM output and gated it — `cpu.pipeline` existed as a net with *zero* flip-flops driving it — and the 56-bit control word rotted between enabled cycles, so the sequencer wandered to a different microcode address every run. The register file failed the same way one level down: instructions ran but register values were wrong, so blink.txt's counter never incremented and the LEDs stayed dark. The rule: a BRAM must read every clock (`CE` tied high) with the value held in fabric flops, or the array must be LUTRAM, which has no output register to decay. After any change, check that no `SPX9` has `CE` wired to the enable.
- Anything clocked that belongs to the CPU takes an `enable` and advances only on it. A bus cycle lasts one *enabled* clock, so an ungated peripheral sees a single CPU write as several board-clock writes. The testbench drives a one-in-two enable rather than a constant `1`: the free-running microcode ROM costs a cycle of latency, so enabled cycles must be at least two clocks apart, and reset has to span several of them.
- Free-running a *synchronous* read is not a substitute for gating it. A write lands in the array on an enabled edge, and a free-running read then exposes the new value partway through the same CPU cycle, where the gated read holds the start-of-cycle value throughout. Tried on the register file; it made the CPU write zeros instead of characters.
- Do not generate the CPU clock in fabric. A divided clock on general routing accumulates ~2.4 ns of skew and nextpnr fails with `Hold/min time violation for clock 'posedge clock'` at the register file block RAM; putting it through a `BUFG` fixes that error but did not work on real hardware. The design now clocks everything from the `in_clk` pin.
- `ram_style = "distributed"` is sometimes needed to keep a memory out of a block RAM: an asynchronous read alone did not stop yosys merging the register file's read register back into a BRAM and gating it again.
- A memory only maps to LUTRAM/BSRAM if its write port is free of an asynchronous reset. The page table used to be written from the main `always @(posedge clock, posedge reset)` block, which forced yosys to emit `Replacing memory ... with list of registers` and spend roughly 4700 LUT4s on it — so much that the table had been cut in half to fit the device. Written from its own `always @(posedge clock)` block it maps to 32 LUTRAM cells and the whole design drops from 45% to 28% LUT4 usage. Treat `Replacing memory ... with list of registers` in the synthesis log as a bug.
- Never wire two module outputs onto the same net. Simulation resolves an undriven output as `z` and lets the real value through, so `make test` passes; yosys instead reports `Driver-driver conflict ... Resolved using constant`, ties the net to `x` and deletes whatever fed it. This silently removed the program RAM and left the CPU fetching a constant on hardware. After changing the bus, check the synthesis log for `Driver-driver conflict` and confirm `tangnano9k.ram.ram_cells` still appears in the `mapping memory` lines.
- The `MUX` serial board in [mux.v](Verilog/mux.v) transmits and receives. Its CPU-side clock enable matters: a bus cycle lasts several board clocks, so a data-register write must start exactly one transmission. `cpu_clock` and `bit_clock` are the same net, which is what lets `tx_request` be a plain flag rather than a clock-domain handshake — separating them would need a real one.
- [programs/hellorld.txt](Verilog/programs/hellorld.txt) cannot drive a *real* UART: it writes all nine characters back to back with no status check, so eight are overwritten before they reach the wire. It only works against the testbench's fake UART, which accepts every write instantly. Use [programs/serial.txt](Verilog/programs/serial.txt) (generated by [MakeSerial.py](tools/MakeSerial.py)) to exercise the real thing — it polls the transmitter-ready bit.
- Treat every yosys `Identifier is implicitly declared` warning as a bug, not noise. `always @(posedge clk)` in the MUX referred to a clock that is not a port of the module (`bit_clock`/`cpu_clock` are), so the block never ran, `int_reqn` was never assigned, and yosys tied the CPU's active-low interrupt request to a constant. CPU6 gates all three microsequencers with `jsr_ = ~(int_enabled & ~int_reqn)`, so the core executed nothing at all on hardware while simulation — which drove `int_reqn` explicitly — passed.
- The two 74LS259 addressable latches, F11 and M13, hold the machine state and are selected by K11 outputs 3 and 2. Both are written as `latch[alu_b[3:1]] <= alu_b[0]`, which is why the wiki lists their functions in pairs. Implemented so far: F11 bit 0 (interrupt enable) and M13 bit 7 (interrupt acknowledge, wired back to the serial board so a request is dropped once taken). The DMA, parity, timer and front panel bits are latched but nothing reads them yet.
- DMA logic is incomplete, and the DP bus sources at `d2d3` 11 and 12 (machine status / interrupt level, and interrupt request level / DIP switches) are still stubs.
- **Driving the board from a script, with no hands.** `openFPGALoader` programs it over libusb, and the UART channel of the same FT2232 opens over libusb too, so `/dev/ttyUSB1` and its `uucp` permissions can be bypassed entirely: `python -m venv`, `pip install pyftdi`, then `pyftdi.serialext.serial_for_url('ftdi://ftdi:2232:/2', baudrate=19200, bytesize=7, parity='N', stopbits=1)`. Sending **`0x02`** asks the design for exactly one status dump, so build, load, run and capture is one script and a hardware iteration costs about three minutes against ten hours of simulation for the same pass. It is **not** NUL - this entry used to say so, and the code says why: at 7N1 a zero byte is a start bit and seven zero data bits, close enough to a break that the receiver often does not frame it, and dumps went missing at random until the character was changed.
- **Instrumentation in `tangnano9k.v` cannot reach into the core with a hierarchical reference.** `cpu.e7` and `cpu.dataInCPU` work perfectly in simulation and silently capture nothing on hardware; the registers survive synthesis, so nothing is optimised away and there is no warning to notice. Anything the top level needs from `CPU6` has to be a real port, which is what the `dbg_` outputs are for.
- **Simulating far enough to reach diag's mapping RAM failure.** The failure is at pass 24704 and the natural simulation rate is about half a pass per wall-clock second, so a run that reaches it takes over twelve hours. `defparam dut.cpu_clock_enable.TICKS = 13;` in the testbench runs the core at roughly 13MHz instead of 5MHz — still the documented minimum of two board clocks between enabled cycles, so cycle-level behaviour is unchanged — and gives 2.9x, about 1.6 passes per second and 4.3 hours to pass 24704. Removing the unused PSRAM controller is not worth it: measured at 6%. The CPU6 core itself is the bottleneck.
- **The re-translation discrepancy does not bite in the first few hundred passes.** Watching every block-move read for a physical address that steps by anything other than one, across roughly 430 passes, found jumps only at block boundaries where a new `PAGE` instruction starts, never within a block, with the entry for that page reading `00` every time. So while the design really does re-translate each byte where the hardware translates once, that difference is not what breaks the early passes. It is not ruled out for later ones.
- **The `PAGE` load loop, traced.** From the fetch of `0x8f04` (`2e 0c f8 01 00`, load 32 entries of map 0 from memory at `0x0100`) the inner loop is `502 503 507 506 448 449 44a 509`. `502`/`503` read the memory byte, `507` sets `page_table_base` to the map being loaded, `506` steps the memory address, `448` swaps the MAR to the entry-select address, `449` is the `k11 == 5` page table write, `44a` restores the base and `509` swaps the MAR back. The entry being written is selected by putting a virtual address whose *page number* is the entry index into the MAR — `0x0006`, then `0x0806`, then `0x1006`, one page apart — with the base set to the map, which is exactly `page_address = {page_table_base, memory_address[15:11]}`. That part of this design is right. The memory side is a virtual address held in `work_address`, reloaded into the MAR and re-translated on every byte, which is the part that is wrong.
- **The remaining mapping RAM failure is entry 0 of the running map, and it is the physical-stepping rule after all.** Driving the board from a script and capturing the last four bytes the compare read before it branched gives `[1fe]=00 [1ff]=00 [100]=00 [200]=01`: the compare wraps to a fresh block and stops at once, with the buffer at `0x100` holding `00` where the reference at `0x200` says `01`. That byte is the table's entry for map 0 page 0 — which is the entry the buffers are themselves addressed through, since `0x100` and `0x200` both live in page 0. So as soon as a `PAGE` load writes a non-zero value there, every later access to those buffers relocates. The earlier measurement that found no mid-block address jumps covered only about 430 passes, during which that entry read `00` throughout; the failure needs a pattern that makes it non-zero, which is why it takes 57345 passes to appear.
- **`dbg_uc_address` is one ahead of the word in the pipeline.** It is the address going into the microcode ROM, and the ROM read is registered, so the word being executed was fetched a cycle earlier. Any trace that prints it is labelling each cycle with the *next* address, which is how `k11 == 1` appeared to be at `0x7e` when it is really at `0xb1`, whose jump target is `0x7e`. Reading fields off the runtime signals is still correct; only the address labels shift.
- **The MAR is virtual and carries the page table index; the work AR carries the memory-side address.** Measured at the page file write: the MAR reads `0x4006`, `0x4806`, `0x5006`, whose page bits are the entry index 8, 9, 10, while the work AR reads `0x0109`, `0x010a`, `0x010b`, stepping one byte at a time. The microcode swaps the two. This rules out the obvious reading of the datapath drawing, in which the mapper sits between the work AR and the bus AR so that the bus AR holds a physical address and increments step physically: that would break the entry-select, which needs the MAR virtual.
- **Leads closed on the physical-stepping mechanism.** `k11 == 0` is idle, not a strobe: bits 0 to 14 of the microcode word are fully packed by `d2d3`, `e6`, `k11`, `h11` and `e7`, leaving no enable bit for the decoder. `d2d3 == 12` never fires at all. `e7 == 1`, the wiki's "bus operation abort", fires four times, all at boot, with the MAR in the register file at `0x00fc` to `0x00ff` — it is the abort for an access to the CPU's own space. F11 bit 3, the wiki's "increment/decrement control", is written during the test at `0x8e7c` but does not control the MAR or work AR step: making either conditional on it hangs the instruction tests in either polarity. What remains unexamined are `h11 == 1` and `h11 == 2`, "begin bus read cycle" and "begin bus write cycle", both bare stubs.
- **The schematic says this design's translation path is already right, and kills the physical-stepping theory.** From `sjsoftware/centurion-cpu6`, whose `kicad/CPU6/CPU6.kicad_sch` is text and can be searched directly (parse `global_label` and `symbol` positions and match by proximity; there are 1260 labels and 585 symbols). The page file is UB9 and UB10, two 93L422s, addressed by `A11`-`A15` together with `MAP0`-`MAP2` and producing `PA11`-`PA17` plus **`RDONLY`** — so the eighth bit is a read-only flag, named as such, confirming it is not an address bit and that the physical address is eighteen bits. `A11`-`A15` come straight off the 74LS669 counters that make up the MAR (UB5, UB6, UC5, UC6), loaded through 74LS157 multiplexers from the R bus. There is **no latch anywhere between the counters and the page file**, so translation is combinational from the live MAR, which is exactly what this design does. Whatever "translate their start address once and then step physically" means in the reference manual, it is not a hardware bypass, and the remaining mapping RAM failure needs a different explanation.
- **Opcode 0x47 is `MEM`, another extended family, and diag's mapping test uses two of its sub-operations.** From the reference manual: the selector byte's high nibble picks the operation, 4 is `MVF`, a byte-wise ascending copy, and 8 is `CPF`, an unsigned byte compare that stops at the first mismatch. Length is the count byte plus one. So `47 40 ff 01 00 02 00` at `0x8e36` **copies** and `47 80 ff 01 00 02 00` at `0x8e90` **compares**, both 256 bytes over `0x100` and `0x200`. The copy runs once per round and builds the reference at `0x200` as a snapshot of the buffer at `0x100`; the loop then does load into the table, store back out, and compares against that snapshot. `0x8e36` is therefore not where the pattern is written, as previously recorded here — it is where the expected answer is captured.
- **The exact failure mechanism, pinned.** diag runs entirely in map 0: all 235604 instruction fetches during the test use base 0, and its buffers at `0x100` to `0x2ff` are reached through map 0 as well. Its code sits at `0x8e00` and up, in page 0x11, so the code is safe, but the buffers are in page 0. On the failing round the pattern gives map 0's entry 0 the value 1. The `PAGE` load writes entries ascending from entry 0 while reading its source at `0x100` upward, so the instant it writes entry 0 its own source relocates from physical `0x100` to `0x900`, and bytes 1 to 255 are read from the wrong place. Byte 0 lands correctly and everything after it is garbage, which is exactly what the board reports. The `MVF` that builds the snapshot is faithful: 0 of 256 bytes differ immediately after it, so nothing upstream is at fault. Note rounds are long, only one in 579 passes, so the failing round is far in.
- **ROOT CAUSE of diag's mapping RAM test failure: `JSR` and `RSR` destroy the X register.** diag's test is a pair of nested loops. The inner one increments one byte of the page table image at `0x120`-`0x1ff` and mirrors it into a reference at `0x220`-`0x2ff`, then loads the whole table from `0x100`, stores it back, and compares the two 256-byte blocks with `CPF`. The outer one steps the pointer with `INRW` and counts down with `DCX`, and is set up by `LDXW #0x0020` at `0x8e82` - 32 bytes, one per entry of a map. What actually happens is that X reads `0x0000` at the top of every outer iteration: it holds `0x0020` at `0x8e8c`, the `JSR` into the PAGE-load routine, and `0x0000` at `0x8e8e` when that routine returns. So `DCX` counts down from zero, the outer loop never terminates on X, and it instead runs until the walking pointer reaches `0x200` - which is the first byte of diag's own reference. Poking that byte breaks the comparison, and the test reports a mismatch at index 0 of `00` against `01`. 224 iterations to walk `0x120` to `0x200` is exactly the 57345 passes the failure is reported on, since the inner loop runs 256 times per outer iteration and 224 * 256 + 1 = 57345.
- **The MAR and work AR count up or down under F11 bit 3, and getting that wrong was breaking every subroutine return.** `h11 == 4` steps the work AR and `h11 == 5` steps the MAR; both were unconditional increments. Meisaka's emulator (`Emulators/Meisaka_Ren/Centurion_files/cen.js` in the Nakazoto repo) is an independent model of the same microcode and settles it: `count_up = (busctl & 8) != 0`, and its `busctl` is this design's `f11` - written by `k11 == 3` from the same microcode fields, with bit 0 the interrupt enable in both. So the direction is `f11[3]`, clear meaning count down, which is what a stack push needs. On hardware `f11` reads `0x4c` while diag runs, so the bit really is being driven. The proof that this was the bug: diag's mapping test routine used to return, via the `RSR` at `0x8ea6`, to `0x8e00`, which is inside the inline string `*** THIS TEST WILL NOT RUN ON CPU-5 ***`; with the direction implemented it returns to `0x8e40`, the next of the eight `JSR`s at `0x8e3d` through `0x8e52` that run the mapping test once per map with arguments 1 to 7 and 0.
- **An earlier attempt at this was recorded as a dead end and should have been re-measured sooner.** The note said driving the two counters from F11 bit 3 garbled diag's menu in one polarity and hung the machine in the other. That was true at the time and is not any more - the blocking faults were the mapping RAM window and the missing RAM at `0x0c000`. This is the second time a remembered negative result outlived the bug that caused it. **Re-measure a blocked experiment against the current tree before believing it.**
- **Where to look in the emulator.** It caches a decoded microcode word per address, and its field extraction agrees with `CPU6.v` bit for bit: `dp_sel` `[3:0]`, `x_e6` `[6:4]`, `x_k11` `[9:7]`, `x_h11` `[12:10]`, `x_e7` `[14:13]`, `aluc_s` `[36:34]`, `aluc_f` `[39:37]`, `aluc_d` `[42:40]`, `aluc_b` `[46:43]`, `aluc_a` `[50:47]`, `f6h6` `[52:51]`, `rir0` `[53]`, `c14_sel` `[55]`, and the microcode constant inverted as `v2 ^ 0xff`. Its register index is `(rir & 15) | (level << 4)` when `c14_sel` and `rir & 255` otherwise, then bit 0 ORed from `rir0` - the same as this design's, and its author notes the hardware NOR there and says they chose not to invert it. Two of its DP bus sources are worth copying: `d2d3 == 8` returns `(entry & 127) | ((entry & 112) == 112 ? 128 : 0)` rather than the raw entry, and `d2d3 == 11` returns `(level << 4) | 4 | (resetting ? 2 : 0) | notpgbit | (dmaint ? 8 : 0)` where this design returns a constant `0x0e` with the flag in bit 0.
- **`psram_controller.v` is Feng Zhou's, from `https://github.com/zf3/psram-tang-nano-9k`, and it has never been built with this toolchain.** Its own header says where it came from, and a diff against upstream shows this copy is that file plus three local changes: the `rst_cnt` width fix, the debug taps, and holding the second die deselected. There is nothing newer upstream to pull. What matters for the open read-path bug is that **upstream builds with the Gowin IDE** - the repository ships a `.gprj`, and its `.cst` has no PSRAM pins because Gowin's tools place those pads themselves. Its README says it "uses Gowin's ODDR/IDDR primitives" and never mentions yosys, nextpnr or apicula. So "it works upstream" is not evidence that it works here, and the difference between Gowin's DDR primitives and apicula's is the most likely home of the fault. The README also gives a maximum of 83MHz, so the 81MHz this design runs it at is within spec.
- **SOLVED, and confirmed on hardware: apicula's ODDR/IDDR cannot be used for the PSRAM, and the fix is an SDR PHY built from fabric flip flops.** `sabas0ba/hello_veryl` has the embedded HyperRAM working on this exact board with yosys, nextpnr and apicula, and `docs/psram.md` says why everything here failed: **the ODDR/IDDR primitives in apicula have roughly 2.5 cycles of data path delay**, so the data never lines up with the clock no matter what the protocol logic does. Their answer was to stop using IOLOGIC altogether and drive the bus with ordinary fabric flops, which got them `PSRAM INIT=1 MEMTEST=PASS` on hardware. That single fact explains every measurement here: the IDDR and ODDR really are placed, the FPGA really does drive and release the pins, the protocol settings really are irrelevant, and upstream's own test fails identically because it uses the same primitives.
- **How their SDR PHY works, from `src/psram/phy_sdr.veryl`.** One HyperBus cycle is built from **four phases of the 27MHz clock, giving CK at 6.75MHz**. Outputs are held stable across all four phases and the FSM only advances on phase 3. CS#, RESET# and the first DQ byte are driven on the 0 to 1 edge; CK rises on 1 to 2 and falls on 3 to 0; the second DQ byte is driven on 2 to 3. Reads are captured **one phase, 37ns, after each CK edge** by a plain flip flop, which is what buys the margin. DQ and RWDS go through ordinary IOBUFs with the output enable driven from fabric. Two bytes still move per CK, so it is HyperBus DDR data with the whole thing clocked from fabric at a quarter rate. 6.75MHz still satisfies the part's tCSM limit of 4us on how long CS# may stay low.
- **What that costs, and the shape of the fix here.** A word access at 6.75MHz is roughly 2us, about ten CPU bus cycles at 5MHz, so every PSRAM access stalls the core by that much. The sensible arrangement is therefore to leave everything the board already answers in block RAM - the ROM, the low RAM, the working RAM at `0x0b000` and diag's stack at `0x0c000` - and let the PSRAM fill the rest of the 256K physical space. diag's whole measured footprint is in the block RAM regions, so it would not slow down at all, while the full complement of memory becomes available to anything that wants it. If that stall ever needs shortening, the levers in order are dropping `SCAN_CK` to just past the data, halving the phase count to put CK at 13.5MHz, and writing CR0 for a shorter initial latency with variable rather than fixed timing - the last of which roughly halves the access on its own.
- **The PSRAM fault is not in this design. zf3's own test fails the same way.** The decisive experiment is to build the upstream test unmodified with this toolchain and run it: `psram_test_top.v`, `psram_controller.v`, `uart_tx.v`, `print.v`, `gowin_rpll/` and `tang9k.cst` from `https://github.com/zf3/psram-tang-nano-9k/tree/main/src`, yosys with `synth_gowin -top memory_test`, nextpnr-himbaechel with their `.cst`, and `gowin_pack` with `tools/sitecustomize.py` on `PYTHONPATH` for the PLL. It reports **FAIL: read wrong data** - its own `TEST_FAIL_READ_WRONG` state. Their pins match this board exactly (clock 52, UART 17), so nothing had to be adapted. **Stop looking for the fault in this project's integration.**
- **Porting the upstream test needs four changes, none of them in the PSRAM path.** `print.v` is an include file, not a module, so it must not be passed to `read_verilog` - `psram_test_top.v` includes it. Its `print` macro uses a SystemVerilog streaming operator, `int_print({>>{a}},b)`, which yosys cannot parse even with `-sv`, so define `NO_UART_PRINT` and report some other way; this project's `StatusDump` works, at 19200 with the divider set for the 81MHz clock and read back with **seven** data bits, because it sets the high bit. There is a malformed `defparam mem_clk_freq=FREQ;` with no instance path that Gowin's parser tolerates and yosys rejects; it refers to nothing and can be deleted. And the test pauses between states, so a periodic dump only ever catches `PAUSE` - latch the first state in the 4 to 8 range instead.
- **What this leaves.** The controller, the test, the clocking and the board are the same as a design its author reports working with the Gowin IDE, and it fails here. So the difference is the toolchain: how yosys, nextpnr-himbaechel and apycula configure the dedicated PSRAM pads and their IO logic, compared with what Gowin's own tools do implicitly. That is where any further work should start, and it is worth checking whether anyone has ever demonstrated this HyperRAM working through the open toolchain at all before spending more on it.
- **Three commonly suggested fixes for a `5555` readback are all wrong here, and one of them does not even build.** A search will offer: drive `O_psram_ck_n`, stop the FPGA driving the bus during reads, and drop the clock to 27MHz bypassing the PLL. All three have been measured and none changes anything - CK# is driven from its own ODDR, `dq_oen` is confirmed to release, and 27MHz behaves exactly like 81MHz. Two details worth keeping. The literal fix usually quoted, `assign O_psram_ck_n = ~O_psram_ck;`, makes nextpnr fail an assertion packing IO logic, because an ODDR output has to reach an IOB directly; the inversion has to go on the data into a second ODDR. And the usual explanation of `5555` - that it is the FPGA's own output latch being read back because test patterns are alternating - does not fit this design at all, which writes `5aa5`.
- **A Reddit thread about Tang Nano 4K versus 9K HyperRAM is worth knowing about, but describes a later problem than this one.** It reports that the default power-on wait between the CA words and the data words is 9 clocks on the 4K and 11 on the 9K, and that a mismatch makes writes land two addresses early - so data written to 2 reads back at 0. That is a *working* interface with shifted data. This design does not have a responding device at all, so that fix does not apply yet; it is the next thing to check once one does respond.
- **apycula cannot pack the rPLL when nextpnr places it on the left of the die, and `tools/sitecustomize.py` works around it.** `get_pll_bels` in `gowin_pack.py` only assigns `offx` inside `if bel.x > 27`, so for a PLL at a lower x it raises `UnboundLocalError` and `gowin_pack` aborts. The shim patches the method at build time: Python's `site` module imports `sitecustomize` from anything on `PYTHONPATH`, so the Makefile's bitstream rule sets `PYTHONPATH` for that one command. Nothing outside the repository is modified, it survives a toolchain reinstall, and it checks the installed source for the missing branch first so it does nothing once the bug is fixed upstream.
- **The vendor PSRAM controller only works at 81MHz as shipped.** Its 160us startup counter is declared `[$clog2(INIT_TIME+1):0]` but incremented as `rst_cnt[14:0] + 1`, hardcoding the width the register happens to have at 81MHz. At 27MHz it is 14 bits wide, bit 14 does not exist, the count never reaches `INIT_TIME`, `rst_done` never rises, and the controller sits in `INIT_ST` for ever with `busy` stuck high. Fixed in `psram_controller.v`; the same trap is waiting in any other frequency dependent width there.
- **The PSRAM is on the CPU's bus and the machine boots on it.** `PsramBus.v` bridges the two: the block RAM goes on answering the ROM, the low RAM and the working RAM, and the PSRAM fills everything else below the I/O page at `0x3f000`. A HyperBus access is about 2.8us, fourteen CPU bus cycles, so the core is stalled for one by **withholding its clock enable** - to CPU6 that is just a long bus cycle, needing no handshake, because it is the enable that would otherwise have moved everything it drives. A **one word cache** is what makes this affordable: there is no read strobe on this bus, the MAR simply sits wherever it last was, so without it every cycle spent pointing into PSRAM would cost a full access whether the microcode wanted the data or not. The cache is only correct because the CPU is the sole writer; DMA would have to invalidate it. `make PSRAM_SELFTEST=1` disconnects the CPU from the memory and runs `PsramTest` against it instead.
- **Hold the core in reset until the memory answers, and never let a memory wedge the machine.** The part needs 600us to come out of its own reset; the core's power on reset is 1024 clocks. Without the extra wait the CPU reaches the memory before the memory exists, and because the bridge holds the enable until an access completes, that is not a slow start but **a hang**: the watchdog blinks the LEDs, diag stops printing, and *the status dump disappears too*, because the request for one is only noticed on an enabled cycle. A stall this design cannot recover from therefore destroys its own instrumentation, which is why `PsramBus` also gives up after 4095 clocks and counts it. Time the whole stall, not just an access in flight - the first version of that timer only covered an access that never finished, and waiting for a controller that never becomes *idle* stalls exactly as hard.
- **ROOT CAUSE of the mapping RAM failure that appeared when the PSRAM went on the bus: `PsramBus` was handing the core two adjacent enabled cycles.** The design's hard floor is two board clocks between enabled cycles, because the microcode ROM, the register file and the board memory are block RAMs that read every clock and need one to settle. `ClockEnable` respects that on its own - five enables in twenty seven are never adjacent - but the bridge withholds the enable during a memory access and hands the withheld pulse back the instant the access finishes, wherever that lands. When it landed one clock before `ClockEnable`'s next pulse, the core took two enabled edges in a row and read a block RAM that had not caught up. One wrong byte, very occasionally: in diag's mapping test the `PAGE` load reads its source a clock early and writes what it got, so an entry reads back as `00` and the compare fails - about one pass in four hundred, and only ever with the PSRAM on the bus, because without it nothing is ever withheld. Fixed with a spacing guard in `PsramBus`; `make test` now checks the invariant, and `PsramBus`'s `ENFORCE_SPACING` parameter lets `MapFailTB` demonstrate the fault rather than argue about it - 160ms gives **14021** adjacent cycles without the guard and **0** with it. Both diag tests print `*** PASS ***` on the board with the PSRAM backing the whole 256K.
- **When a stall is added anywhere near the core's clock enable, check the spacing, not just the logic.** The bug above looks like a memory or MMU fault from every angle the status dump can see - a page table entry that reads back wrong - and three separate measurements ruled the obvious causes out before the real one surfaced: no bus read and no bus write ever went through a map other than 0, so the `PAGE` block move's base save and restore is correct, and both clocked blocks in `CPU6` are properly enable-gated. The fault was not in what the core did but in when it was allowed to do it.
- **Instrumentation that reports a count of something ambiguous will mislead you.** A counter of "page table entries written as zero with a non-zero index" looked like a clean anomaly detector and is not: diag installs maps from buffers that legitimately hold zeros, so the count keeps rising even on a healthy run. It stayed at 8 per 2238 passes after the fix, which briefly looked like the fix had failed. Prefer a detector whose zero case is unambiguous.
- **Two dump-reading traps, both of which cost a round each.** The status dump only answers while diag is reading the serial port, and during a soak test it is not - so "no dump" during a run means the machine is busy, not broken, and the dump only starts answering again once the test fails and diag returns to a prompt. And the dump's payload must mean the same thing in every build being compared: the PSRAM self test's result used to replace the running summary in a `PSRAM_SELFTEST` build, so the same five hex words meant different things in the two builds being held up against each other. Both now have their own marker letter.
- **The PSRAM works. `PsramSdr.v` is the PHY and `make psramtest` is its regression test.** Measured on the board: the self test passes including byte writes, the command loopback reads back `a000` so the data pins really are driven, and the bring-up scan finds the returned data at **CK 12 after the command** - exactly twice the initial latency of six, confirming the part's power-on `CR0` of `8f1f` without ever writing it. The scan reports the bus going active at CK 10, two cycles ahead of the data, as the die takes the bus over. Three plumbing bugs stood between the working PHY and the working PHY, all of them found in simulation against `HyperRamModel.v` rather than on the board: **a HyperBus word is the two bytes either side of one CK cycle and its second byte is only sampled during the first phase of the *next* cycle**, so a naive `{rx_a, rx_b}` pairs each rising-edge byte with the *previous* cycle's falling-edge byte - both bytes are correct on the wire, so a logic analyser would show nothing wrong; write data was being driven after two CK instead of the full fixed latency; and CS# was rising on the same edge that produced the last CK edge, which both violates the part's CS# hold time and leaves one CK edge pair happening while RWDS floats, which a write burst reads as "write this byte too" and so silently appends a word of rubbish to every write.
- **A module that relies on the FPGA zeroing its flip flops must say so with an `initial` block, or it is dead in simulation.** `PsramSdr`'s state registers had none. On the board that costs nothing - configuration clears every flop, and `resetn` is the reset button, which is pulled up and never pressed, so the state machine walks out of `S_RESET` by itself and pulses the part's RESET# on the way. But the board level testbenches hold that button released too, so the reset branch never runs and every one of those registers stays `x` for the whole run. RESET# being `x` is enough on its own for the behavioural die to ignore the bus completely: **0 bursts against 64 accesses the bridge believed it had made**. Every read then came back as `z`, which reaches the CPU as a byte of `x`, poisons whatever address is computed from it, and stops the machine with no memory access ever attempted. This is why the FORTH's memory sizer reported 12K - exactly the six block RAM pages - and why `probe17.s` hung on its first window read. With the `initial` block it reports **244K**, which is 122 of the 128 physical 2K pages, the six missing being the 8K ROM and the I/O and boot pages. None of this was ever visible on hardware, where the memory worked the whole time.
- **When a simulated machine simply stops, find out whether it is stalled or has stopped fetching, and do it first.** `make run ... RUNARGS=+psramtrace` reports what the bridge, the microcode and the PHY were doing when no instruction was fetched for 20000 clocks, and `+pctrace` names every fetch. In the case above the answer - core parked at microcode `0x285` with the MAR reading `xxxx`, and the bridge idle - ruled out the memory bridge in one run and pointed straight at X propagation. Guessing at the cache, the write path and the address decode beforehand cost several rounds and was wrong every time.
- **A behavioural HyperRAM model is worth far more than it costs.** `PsramTest.v` used to carry a note saying only hardware could answer whether the controller talked to the part. True of the part, false of the plumbing, and the plumbing is where all three bugs were. A build-load-capture cycle on the board is about three minutes; `make psramtest` is a second.
- **nextpnr's `IOB:` utilisation row does not count `IOBUF` cells, so do not read the PSRAM pads as missing.** The netlist had 17 `OBUF` + 4 `IBUF` + 18 `IOBUF` and nextpnr reported `IOB: 21/276`, which looks exactly like every bidirectional pin having been dropped and sent a whole investigation the wrong way. They were all placed. To check placement properly, read `NEXTPNR_BEL` off the cells in the post-pnr JSON and compare against apicula's own table: `chipdb.load_chipdb('apycula/GW1N-9C.msgpack.xz').sip_cst['GW1NR-9C']['QFN88P']` lists every PSRAM pad as `(name, row, col, bel, iostd)` - `IO_psram_dq[0]` at row 1 bel B through `IO_psram_dq[15]` at row 26 bel A, with `IO_psram_rwds` at rows 16 and 26. The low half of DQ with `cs_n[0]`, `ck[0]` and `rwds[0]` is the first die; the high half is the second, which this design leaves deselected.
- **The PSRAM was never actually connected before this.** The controller was instantiated but the top level had no PSRAM ports, so every `O_psram_*` and `IO_psram_*` net was implicitly declared and went nowhere. The old comment claiming the pins were held at defined levels was wrong. nextpnr's chip database names the dedicated pads, so the ports have to be named exactly `O_psram_ck`, `O_psram_cs_n`, `O_psram_reset_n`, `IO_psram_rwds` and `IO_psram_dq` and it places them itself - no `.cst` entries. `O_psram_ck_n` must be left alone: an ODDR output has to reach an IOB directly, and fanning it into an inverter as well makes nextpnr fail an assertion while packing IO logic.
- **`PsramTest.v` is the bring-up harness and follows its own advice.** The SD card design note argues for proving a memory layer standalone before wiring it to the bus, and that is what found both bugs above. It runs in the controller's clock domain with no CPU involvement, writes six words spread across the die and reads them back, and reports through the status dump. When reading its results, remember the payload is exactly 80 bits: an 81 bit concatenation shifts every printed word and produced a completely misleading reading of this test - `busy` low and the write stuck - before the width was corrected.
- **The Diag board is a real device and now has its own module, [DiagBoard.v](Verilog/DiagBoard.v).** It carries a two digit hex display with four decimal points and a bank of DIP switches, at physical `0x3f100`. Everything but `0x3f110` is a *touch* register: the side effect happens on a read as much as on a write and the data is ignored, which is how Meisaka's emulator models it. `0x3f110` is the display on write and the switches on read. It used to be two hardcoded bytes inside `BoardMemory`.
- **The DIP switches choose what the machine does out of reset, and that is how to reach TOS.** diag reads them at `0x8030`, masks to four bits, special cases `0x0d` to the auxiliary test menu, and otherwise uses the value to index a jump table at `0x8055`. The settings are `0x11`/`0x13` DMA tests, `0x16` the MUX interrupt test, `0x17`-`0x19` the Hawk disk tests, **`0x1a` TOS**, and `0x1d` the auxiliary tests. Bit 7 must be clear or `0x8045` restarts. Build a setting with `make DIP=1a`; the default is `1d`.
- **TOS, the machine code monitor, is in the diag ROM at `0x846f` - it is not loaded from disk.** It announces itself by printing its own address and prompts with a backslash. `M` followed by a hex address examines memory, space steps forward, and typing a value writes one; `G` runs from an address and `Q` restarts. The console primitives sit just below it: `0x8500` reads a character, `0x850e` writes one, `0x8519` prints a byte as two hex digits. Verified on hardware - `M8001` then spaces gives `3A B1 B8 00 05`, exactly what `diag.txt` holds there. **The address follows `M` with no space**: `M 8001` is read as `M`, a step, and then the address `008001`, which is a different and confusing thing.
- **TOS runs on the full memory, and [TosMemTest.py](tools/TosMemTest.py) proves it.** `make DIP=1a`, load, then run that script: it writes one address dependent byte into every 2K page the running map reaches and reads them all back. All 26 RAM pages pass. Unlike `PsramTest`, which exercises the memory controller on its own, this goes through the CPU, the MMU and the bus, so it is the check that says the machine can *use* its memory. The reads before writing are themselves informative - the block RAM regions read `00` and the PSRAM reads uninitialised rubbish like `4A A5 55 55`, which is what a real HyperRAM looks like out of reset.
- **The top 4K of virtual memory is the I/O page, not RAM.** The running map points virtual pages 30 and 31, `0xf000`-`0xffff`, at physical `0x3f000`, so virtual `0xf110` reads the Diag board's DIP switches - it returns `1a` on a `DIP=1a` build, which is how this was confirmed - and virtual `0xf200` is the MUX. It is *not* the identity map that `ptinit` installs; diag remaps those two pages so software can reach the devices, exactly as the real machine does. Writing there through TOS takes the console away and the monitor stops answering, which looks precisely like a memory fault in the top two pages and is nothing of the sort. A memory sweep must skip pages 30 and 31 as well as the ROM at `0x8000`-`0x9fff`.
- **There is an assembler now: [Assemble.py](tools/Assemble.py).** Programs used to be hand written as hex bytes, which is fine for a blink loop and hopeless for anything larger. It emits the same `programs/*.txt` format so nothing downstream changes. Its opcode table is embedded rather than read from the reference manual at run time, and `--verify opcodes.yaml` cross checks the two. The encodings are confirmed against real code rather than against a reading of the manual: `--roundtrip Verilog/programs/diag.txt 8000` disassembles the diag ROM, re-encodes every instruction in the form the ROM actually used and compares bytes - **3812 instructions, all identical**. Re-run that after any change to it; it is what found three instruction length bugs in `Disassemble.py`.
- **`make run SRC=x.s IN=input.txt` assembles a program and runs it on the whole simulated board**, typing an input file at it over the serial line and printing what comes back. That is a one second loop against three minutes for a build, load and capture on hardware, and it is what makes writing anything substantial for this machine practical. The ROM's program is a parameter now, with a `+prog=` plusarg for simulation and `make PROGRAM=...` for synthesis - the latter only started working when `-DSYNTHESIS` was added to hide that plusarg from yosys, which cannot resolve `$value$plusargs` while re-elaborating `BoardMemory`, and re-elaborating it is exactly what setting the parameter makes it do. The typist paces itself against the MUX's own receiver rather than against a delay - see the note on that below, because getting it wrong is what made a board fault look like a program fault for a whole afternoon. `RUNARGS=` passes plusargs through: `+pctrace`, `+psramtrace`, `+typetrace`, `+rxtrace`.
- **Things about this instruction set that only running it will tell you.** Every one cost a debugging session, and several are the opposite of the obvious reading. They are recorded in `Verilog/asm/probe*.s`, which are small programs that print the answers.
  - **A post-increment steps by two for a word and one for a byte**, so `[Y++]` walks a list of addresses correctly.
  - **`JMP [X]` jumps to the address in X; `JMP [[X]]` jumps to what X points at.** diag's own DIP switch dispatch settles it - it loads a table entry into A and then does `JMP [A]`. Those two instructions plus `LDX [B++]` are an indirect threaded inner interpreter.
  - **`XAB`, `XAX`, `XAY`, `XAZ`, `XAS` are moves *out of* A, not exchanges**, despite reading like swaps. There is no move the other way in that family, and `XFR` does not fill the gap. Only A, B and X can be the destination of a load or the source of a store, so anything that has to be saved has to be in one of those three.
  - **`SUB B,A` leaves its answer in A**, not in B, while **`AAB` and `NAB` leave theirs in B**. The register-to-register `ADD` and `AND` do not put the result anywhere useful at all. So: subtract with `SUB B,A` and read A; add and mask with `AAB` and `NAB` and read B.
  - **Only `SUB B,A` sets the sign flag.** The implicit `SAB` does not, so `BM` after one tests something stale. For the *unsigned* comparison use **`BNL`**, not `BL`: `BL` is branch-if-Link, and Link is set when the subtraction did **not** borrow, so `BNL` is "less than" and `BL` is "greater or equal". This entry used to say `BL` was the borrow, which is backwards, and acting on it turned a number printer that was wrong for one class of value into one that printed `0` for every value.
  - **Print unsigned magnitudes with `BNL`, and remember that `BM` looks tiny to anything with bit 15 set.** The FORTH number printer compared the running value against each power of the base with the signed `BM`, so in any base but ten a value from `0x8000` up looked smaller than every power and came out as `0` - `HEX` then `8000 .` printed `0`. Base ten hid it completely, because that is the one base the printer handles the sign for, and after negating, the value is always below `0x8000`.
  - **`BM` and `BP` are not complements.** After a subtraction `BM` behaves and `BP` does not. An assembler that relaxes a long `BM` into `BP` over a jump produces a loop that never ends and looks exactly like a bug in the loop; `Assemble.py` branches on the *same* condition over an extra jump for that reason.
  - **`ORI` is inclusive OR, `ORE` is exclusive, and `IVA` inverts A. Like `SUB B,A`, the two ORs leave the answer in their *second* operand** - `ORI B,A` puts it in A - which is the opposite way round from `AAB` and `NAB`, whose answer lands in B. Measured in `probe18.s`, which runs each one both ways round and prints both registers.
  - **`SRR` is an arithmetic right shift, and both shifts move one place more than their count field holds.** `SLR A,4` shifted five places before `Assemble.py` learned to bias them the way it always has `INR` and `DCR`. A round trip cannot catch a wrong bias, because the assembler and the disassembler share that table - it has to be measured on the machine. `CLR` and `IVR` take the same kind of field and have *not* been measured, so they are deliberately left unbiased.
  - **`MUL` and `DIV` work, and diag never uses either, so nothing in the ROM shows how.** `DIV B,A` takes the dividend in A and the divisor in B and leaves the **remainder in A and the quotient in B**; `MUL B,A` leaves the low word of the product in B and the high word in A. Measured in `probe19.s`. The FORTH's `*` was a shift-and-add loop for want of this.
  - **Z and S can be read even though nothing can move out of them.** Only A, B and X can be the source of a store, and the `XAZ` family only moves *into* Z - but Z can be an operand of an ordinary arithmetic instruction, so `CLA` followed by `SUB Z,A` leaves the data stack pointer in A. That is what makes a run-time index into the stack possible at all, and it is how `PICK` is written.
  - **A byte load leaves the high half of the register alone**, so any byte that is going to be used as a number needs `CLA` in front of the load. And a store sets no flags, so the sign of a value has to come from an arithmetic operation on it.
- **A FORTH primitive that loads B must park the instruction pointer first.** B is the interpreter's instruction pointer, so `LDB [Z++]` to fetch a second argument destroys it and the machine restarts on the next word. The existing `AND` saves it in `ipsave3` and restores it; writing `OR` and `XOR` alongside it without doing the same crashed on the first line that used them. The primitives that move B on purpose - `EXIT`, `BRANCH`, `LIT`, `DOCOL` - are the exception, and must *not* save and restore it.
- **A helper called with `JSR` must not touch X.** `JSR` puts the return address in X and pushes the old X; `RSR` jumps to X and pops. So `LDX` anywhere in a subroutine destroys its own return address, and the routine returns to whatever it last pointed at. Use **Y** to point with - `XAY` loads it from A, and every addressing mode takes any register as the pointer - and leave X alone. This was a whole afternoon.

It needs the reference manual's `data/opcodes.yaml`, which is not vendored. The subtlety it encodes: the table names the *destination* mode in `mode` and the *source* in `src`, and either can be the implicit register form, so an instruction's length comes from whichever of the two is not implicit.
- **The real boot PROM is recoverable from the emulator, if it is ever wanted.** `cen.js` embeds it as base64 in `bpl_rom`, scrambled: the loader inverts the address and permutes its bits with `remap = [0,1,2,3,4,8,5,6,7]`, so `image[a] = raw[remap(a ^ 511)]`. Descrambled, it holds `JMP 0xfc00` at offset `0x100` - the reset vector, which physical `0x3fd00` supplies - and begins with a test and a `JMP 0x8001` into the diag ROM. - **Do not add a level triggered fallback to the status dump.** It was tempting: a machine that has stopped reading the MUX data register never produces another rising edge of `byteReady`, so the edge triggered dump cannot be asked for a dump exactly when one is most wanted. - **Driving diag over the serial line: the menu needs a terminating keystroke, and the status dump supplies one.** Typing `02` only echoes; the test starts on the *next* character, whatever it is. - **A transmit write used to discard a received byte, and that is the second time the missing read strobe has bitten.** This bus has no read strobe of its own: the address register simply stays where it was until something needs it again. So the cycles after the CPU writes the MUX's transmit register still have that register on the address bus with `write_en` gone, and the next read strobe reads as the CPU *taking* a received byte - throwing away whatever had arrived. Every character the machine printed could eat one it had been sent. A person typing at a terminal can never see this, because they cannot type inside one character time; feeding a file at line rate shows it at once, as input lost in bursts exactly while the machine is busiest. `mux.v` now ignores a read of the data register until the address bus has moved off it, which a genuine read always does via the instruction fetch that issued it. The same hazard is why `PsramBus` has a one word cache; treat any device whose *read* has a side effect as suspect on this bus.
- **Pacing the simulated typist: neither level of the receiver flag is a handshake on its own.** Waiting for it to clear is not one, because it is set as the stop bit completes - a moment after `send()` returns it is still low, and the next byte goes out on top of one the machine has not taken. Waiting for it to be *set* after sending hangs, because the program can read the byte out within a few cycles of its arriving. And silence is not readiness either: the machine is silent precisely while it is compiling. `ProgramTB` pairs the empty flag with the receive count, which only ever goes up, and bounds both waits. - **The MUX raises an interrupt only on receive.** There is no transmit-ready and no timer interrupt, and `int_pending` is set solely on the rising edge of `byteReady`. - **ROOT CAUSE, confirmed: the board has no RAM where diag puts its stack.** `CPU6`'s `JSR` does not push the return address - it puts the return address in **X** and pushes the **old X** onto the stack, and `RSR` pops X back. diag's stack pointer is `0xc002`, which translates to physical `0x0c000`, and `BoardMemory` decoded RAM only at `0x0b000`-`0x0bfff`. - **How to find the memory the machine actually needs.** Count bus reads and writes per 2K physical page over a run and print the histogram. - **The register file addressing is a bit permutation of the hardware's, not a fault.** The schematic puts the level on A0..A3 (bit reversed, through `UC14` selected by `PL55`), the register number `RIR[3:1]` on A4..A6, and the byte select on A7. `CPU6.v` puts the level on A4..A7, the register number on A1..A3 and the byte select on A0. Both are built from the same signals, so the mapping from one to the other is a bijection and the collision behaviour is identical - it only relabels rows of the array. - **`~(PL53 | RIR0)` really is the byte select, exactly as `CPU6.v` has it.** An earlier reading of this schematic said the NOR took `RIR0` and `RIR4`. - **Where X goes.** Logging every register file write during the `JSR`/`RSR` pair shows two of them addressing word register 2, which is X at bytes `0x04` and `0x05`: the call writes the return address `0x8e8e` there and the return writes `0x0000`. - **A diag test that returns to the menu has not necessarily passed.** The mapping RAM test used to come back looking fine while actually having crashed: it ran off into the empty register file region, executed 254 zero bytes, came out the far side and recovered through `0x808b`'s `JMP 0x0000`. `make diagtest` now fails if the machine ever executes below `0x0100`, which is the honest check. The test itself runs until it is sent a control-C rather than terminating on its own.
